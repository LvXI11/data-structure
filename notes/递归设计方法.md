# 递归函数设计方法

> 能默写 ≠ 能设计。能设计 = 照着四步流程推导出一个**没见过**的递归函数。
> 第一个自己设计的成功案例：`count_even`（统计偶数节点，2026-09-05）。

## 设计四步法（每次写递归前走一遍）

**核心心法：永远只站在一个节点上看问题，绝不往下看。**

| 步骤 | 问自己 | 示例：count_even |
|---|---|---|
| ① 问题 | 这个函数回答什么问题？ | 数出子树里值偶数的节点个数 |
| ② 出口 | 最简单的情况（空树）返回什么？ | 空树 → 0 |
| ③ 局部视角 | 站在根上，只看眼前：结果 = 我贡献的 + 什么？ | 我的值偶数就贡献 1（`T->e%2==0`）+ 左边几个 + 右边几个 |
| ④ 信任 | "左边几个"谁算？→ 调自己 | `count_even(T->lchild)` |

写成代码就是万能骨架：

```c
int f(Tree* T){
    if(T==NULL) return 0;                     // ② 出口
    return [我贡献的] + f(T->lchild) [+ f(T->rchild)];  // ③④
}
```

## 设计时的三个纪律

1. **绝不往下看**——设计只发生在"我这一层"：我贡献什么 + 两边交给递归。往下看（人肉展开）是复现代码的人做的事，设计者从不展开。
2. **每个节点只被"问"一次**——函数只回答一个问题，别把两个问题混在一个函数里（乱，就是因为同时想两个问题）。
3. **出口先写对**——空树返回什么想清楚，其余都是"信任递归"的填空。

## 已验证的案例（同一副骨架）

| 函数 | 出口 | 站在根上的"我贡献 + 两边" |
|---|---|---|
| count_node 节点数 | 0 | `1 + 左 + 右` |
| get_height 树高 | 0 | `1 + max(左高, 右高)` |
| count_leaf 叶子数 | 0 | 我是叶子→1；否则 `左叶 + 右叶` |
| **count_even 偶数个数**（自设计） | 0 | `(我%2==0) + 左 + 右` |
| sum_tree 所有值之和（演示） | 0 | `我的值 + 左 + 右` |

## 自测练习（能独立设计这些 = 递归毕业）

1. `count_odd(T)`：奇数节点个数（count_even 的孪生）
2. `max_value(T)`：整棵树的最大值（提示：出口返回什么？空树没有最大值——想想怎么处理，或者约定返回一个极小的数）
3. `count_node_degree2(T)`：度数为 2（左右孩子都有）的节点个数
4. `count_full(T)`：所有节点值之和的整数倍……（编一个自己的问题练手）

> 设计流程重复够多次后，"信任"会变成直觉——那时候递归就不是"想出来的"，是"顺手写出来的"。
